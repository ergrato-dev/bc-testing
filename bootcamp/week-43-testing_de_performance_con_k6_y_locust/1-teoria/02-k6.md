# 02 - k6

> Herramienta: **k6** 2.3.0 (Grafana Labs). Scripts en JavaScript

**k6** es un generador de carga escrito en Go. Los scripts se escriben en JavaScript, pero no se ejecutan en Node: k6 trae su propio intérprete, y cada usuario virtual (**VU**) ejecuta el script en un entorno aislado. Por eso no hay `package.json`, ni `pnpm install`, ni módulos de Node como `fs`. Los módulos se importan de `k6/...`.

---

## 🎯 Objetivos

- Instalar k6 y escribir un script con peticiones, comprobaciones y esperas.
- Describir la carga con `vus`, `duration`, `stages` y escenarios con *executors*.
- Leer el resumen de k6 y convertir los criterios de aceptación en umbrales que deciden el código de salida.
- Etiquetar las peticiones para medir y exigir cada una por separado.
- Guardar los resultados en JSON y en un informe HTML.

---

## 1. Instalar k6

k6 es un único binario. La versión del curso es la 2.3.0 ([stack-versions](../../../docs/stack-versions.md)).

| Sistema | Instalación |
|---|---|
| Linux y WSL | Descarga el binario de la release y cópialo a `~/.local/bin` (pasos debajo) |
| macOS | `brew install k6` |
| Windows | `winget install k6 --source winget` |
| Cualquiera con Docker | `docker run --rm -i --network host grafana/k6:2.3.0 run - <script.js` |

En Linux:

```bash
curl -sSLO https://github.com/grafana/k6/releases/download/v2.3.0/k6-v2.3.0-linux-amd64.tar.gz
tar xzf k6-v2.3.0-linux-amd64.tar.gz
install k6-v2.3.0-linux-amd64/k6 ~/.local/bin/k6
k6 version
# k6 v2.3.0 (commit/e088784614, go1.26.8, linux/amd64)
```

| Paso | Qué / Para qué |
|---|---|
| `curl -sSLO` | Descarga el archivo con su nombre original (`-O`), siguiendo redirecciones (`-L`) y mostrando solo los errores (`-sS`) |
| `tar xzf` | Descomprime el `.tar.gz` en `k6-v2.3.0-linux-amd64/` |
| `install ... ~/.local/bin/k6` | Copia el binario con permisos de ejecución a una carpeta que ya está en tu `PATH` (`echo $PATH` lo confirma) |

Con Docker, `--network host` hace que `localhost` dentro del contenedor sea tu equipo, y `run -` lee el script de la entrada estándar.

## 2. El script

```js
import http from 'k6/http';
import { check, sleep } from 'k6';

const BASE_URL = 'http://localhost:18043';          // código init: una vez por VU

export function setup() {                            // una vez, antes de empezar
  const res = http.get(`${BASE_URL}/health`);
  if (res.status !== 200) throw new Error('la API no responde');
}

export default function () {                         // cada iteración de cada VU
  const res = http.get(`${BASE_URL}/api/books/9780000000001`);
  check(res, {
    'status is 200': (r) => r.status === 200,
    'is the requested book': (r) => r.json('isbn') === '9780000000001',
  });
  sleep(1);
}
```

| Pieza | Qué / Para qué |
|---|---|
| Código *init* | Lo que está fuera de las funciones. Se ejecuta una vez por VU, al crearlo: constantes, `open()` de archivos de datos |
| `setup()` | Una vez antes de la carga. Lo que devuelve llega como argumento a `default` y a `teardown`. Sirve para comprobar el sistema o preparar datos |
| `default` | Una **iteración**. Cada VU la repite mientras dure la prueba |
| `teardown()` | Una vez al terminar, para limpiar |
| `http.get`, `http.post`, `http.del` | Peticiones. Devuelven la respuesta con `status`, `body`, `headers` y `json()` |
| `check(res, {...})` | Comprobaciones con nombre. Se cuentan en la métrica `checks`, pero **no detienen el script ni hacen fallar la prueba** ([lab 01](../2-practicas/lab-01-primer-test-de-carga-con-k6/README.md#experimento-1-un-check-que-falla)) |
| `sleep(1)` | El tiempo que una persona tarda en leer el resultado (*think time*). Sin él, cada VU dispara peticiones sin parar |

Las URLs con datos variables se escriben con `encodeURIComponent`: `?q=${encodeURIComponent('faro gris')}`. Un espacio sin codificar produce una URL que el servidor rechaza con 400.

`http_req_failed` cuenta como error toda respuesta fuera de 200–399. Si en tu sistema un código 4xx es una respuesta correcta (un 409 cuando el libro ya está prestado), díselo a k6:

```js
http.setResponseCallback(http.expectedStatuses({ min: 200, max: 399 }, 409));
```

## 3. Las opciones: cuánta carga y con qué forma

Las opciones van en `export const options` o en la línea de comandos, que tiene prioridad.

```js
export const options = {
  stages: [
    { duration: '10s', target: 30 },   // subida: de 0 a 30 VUs en 10 s
    { duration: '30s', target: 30 },   // meseta: 30 VUs durante 30 s
    { duration: '10s', target: 0 },    // bajada
  ],
};
```

| Opción | Qué hace | En la línea de comandos |
|---|---|---|
| `vus` + `duration` | Un número fijo de VUs durante un tiempo | `--vus 10 --duration 30s` |
| `iterations` | Un número total de iteraciones, repartidas entre los VUs | `--iterations 100` |
| `stages` | Tramos con un objetivo de VUs: k6 sube o baja en línea recta hasta él | `--stage 10s:30,30s:30,10s:0` |
| `scenarios` | Uno o varios escenarios, cada uno con su *executor* | No |

Un **escenario** describe la carga con un *executor*. `vus`, `duration` y `stages` son atajos de los dos primeros de esta tabla:

| *Executor* | Modelo | Qué fijas |
|---|---|---|
| `constant-vus` | Cerrado | VUs y duración |
| `ramping-vus` | Cerrado | Tramos de VUs (`stages`) |
| `constant-arrival-rate` | Abierto | Iteraciones por segundo (`rate`, `timeUnit`), duración y VUs disponibles (`preAllocatedVUs`, `maxVUs`) |
| `ramping-arrival-rate` | Abierto | Tramos de iteraciones por segundo |
| `shared-iterations`, `per-vu-iterations` | — | Un número de iteraciones: para datos de prueba, no para medir |

```js
export const options = {
  scenarios: {
    search: {
      executor: 'constant-arrival-rate',
      rate: 40,              // 40 iteraciones...
      timeUnit: '1s',        // ...por segundo
      duration: '30s',
      preAllocatedVUs: 20,   // VUs creados al principio
      maxVUs: 200,           // VUs que puede añadir si la API se vuelve lenta
    },
  },
};
```

Con `constant-arrival-rate`, k6 inicia 40 iteraciones por segundo pase lo que pase ([teoría 01](01-performance-testing.md#5-modelo-cerrado-y-modelo-abierto)). En este modelo no se usa `sleep`: el ritmo ya lo marca el *executor*.

## 4. El resumen

Al terminar, k6 imprime el resumen (en la versión 2, el modo `compact`; `--summary-mode=full` añade el detalle por escenario y grupo):

```text
  █ TOTAL RESULTS

    checks_total.......: 1096    32.218255/s
    checks_succeeded...: 100.00% 1096 out of 1096
    checks_failed......: 0.00%   0 out of 1096
    ...
    HTTP
    http_req_duration..............: avg=55.07ms min=451.2µs med=54.2ms max=175.76ms p(90)=111.23ms p(95)=118.89ms
      { expected_response:true }...: avg=55.07ms min=451.2µs med=54.2ms max=175.76ms p(90)=111.23ms p(95)=118.89ms
    http_req_failed................: 0.00%  0 out of 548
    http_reqs......................: 548    16.109128/s

    EXECUTION
    iteration_duration.............: avg=1.11s   min=1.04s   med=1.1s   max=1.21s    p(90)=1.14s    p(95)=1.15s
    iterations.....................: 274    8.054564/s
    vus............................: 4      min=4        max=10
```

| Métrica | Qué es |
|---|---|
| `http_req_duration` | Envío + espera + recepción de cada petición. Es la latencia que importa |
| `{ expected_response:true }` | La misma, sin las respuestas de error. Si es muy distinta de la general, los errores están cambiando la latencia |
| `http_req_failed` | Proporción de respuestas inesperadas |
| `http_reqs` | Peticiones: total y por segundo |
| `iteration_duration` | Lo que tarda una vuelta entera de `default`, esperas incluidas |
| `vus` | VUs activos: el valor al terminar, el mínimo y el máximo |
| `checks_*` | Comprobaciones cumplidas y fallidas |

Para las métricas de tiempo, k6 muestra `avg min med max p(90) p(95)` por defecto. `--summary-trend-stats "med,p(95),p(99)"` elige otras.

## 5. Umbrales: los criterios de aceptación

Un **umbral** (*threshold*) es un criterio sobre una métrica. Si alguno no se cumple, k6 termina con el **código de salida 99**, y un pipeline de integración continua falla.

```js
export const options = {
  thresholds: {
    http_req_failed: ['rate<0.01'],      // menos del 1 % de errores
    http_req_duration: ['p(95)<300'],    // p95 por debajo de 300 ms
    checks: ['rate>0.99'],               // más del 99 % de comprobaciones cumplidas
  },
};
```

```text
  █ THRESHOLDS

    checks
    ✓ 'rate>0.99' rate=100.00%

    http_req_duration
    ✓ 'p(95)<300' p(95)=64.54ms

    http_req_failed
    ✓ 'rate<0.01' rate=0.00%
```

| Tipo de métrica | Ejemplo | Expresiones |
|---|---|---|
| *Trend* (tiempos) | `http_req_duration` | `avg`, `med`, `p(N)`, `max`, `min` |
| *Rate* (proporciones) | `http_req_failed`, `checks` | `rate` |
| *Counter* (cuentas) | `http_reqs` | `count`, `rate` |

Un umbral con `abortOnFail: true` detiene la prueba en cuanto se incumple, en lugar de esperar al final. `delayAbortEval` le da un margen para que unas pocas peticiones lentas del arranque no la corten:

```js
'http_req_duration{name:search}': [{ threshold: 'p(95)<100', abortOnFail: true, delayAbortEval: '10s' }],
```

## 6. Etiquetas: una métrica por petición

Cada petición lleva **etiquetas** (*tags*): `method`, `status`, `url` y `name`, que por defecto es la URL. Un umbral puede filtrar por etiqueta con `métrica{etiqueta:valor}`:

```js
const book = http.get(`${BASE_URL}/api/books/${isbn}`, { tags: { name: 'book' } });
const found = http.get(`${BASE_URL}/api/books?q=${q}`, { tags: { name: 'search' } });

export const options = {
  thresholds: {
    http_req_duration: ['p(95)<300'],
    'http_req_duration{name:book}': ['p(95)<50'],
    'http_req_duration{name:search}': ['p(95)<100'],
  },
};
```

Fijar el `name` hace dos cosas. Agrupa las URLs que solo cambian en un dato: sin él, cada ISBN sería un `name` distinto, con su propia serie de métricas. Y permite exigir a cada petición lo suyo. En el [lab 02](../2-practicas/lab-02-umbrales-etapas-y-etiquetas/README.md#paso-5-un-umbral-por-petición-paso-3), con 150 VUs, el p95 global cumplía (144 ms < 300 ms) mientras la consulta y la búsqueda incumplían las suyas: el percentil global mezclaba las dos y escondía el problema.

El resumen solo muestra las submétricas que usa algún umbral. Y un umbral sobre una etiqueta que ninguna petición lleva (un `name:books` mal escrito) se evalúa sobre una submétrica vacía, vale `0s` y **se cumple** ([lab 02, experimento 2](../2-practicas/lab-02-umbrales-etapas-y-etiquetas/README.md#experimento-2-sin-la-etiqueta-name)).

## 7. Guardar los resultados

| Para | Cómo | Qué produce |
|---|---|---|
| Comparar ejecuciones o leer los números desde un script | `k6 run --summary-export results/summary.json script.js` | El resumen en JSON |
| Un informe para personas | `K6_WEB_DASHBOARD=true K6_WEB_DASHBOARD_EXPORT=results/report.html k6 run script.js` | Un HTML autocontenido con gráficas de peticiones, latencias y VUs en el tiempo |

Del JSON se lee un número con `jq`:

```bash
jq '.metrics["http_req_duration{name:search}"]["p(95)"]' results/summary.json
# 77.819237
```

Dos trampas de ese JSON: en los umbrales, `false` significa que **no** se incumplió (`"thresholds": {"p(95)<100": false}` es un umbral cumplido). Y en una métrica *Rate*, `passes` cuenta los valores verdaderos: en `http_req_failed`, `"fails": 1202` son 1202 peticiones que no fallaron.

El informe HTML necesita una ejecución de cierta duración. Con 5 s, k6 avisa: `The test run was short, report generation was skipped (not enough data)`.

---

## ✅ Resumen

- k6 es un binario: scripts en JavaScript, sin Node ni `package.json`. La función `default` es una iteración, y cada VU la repite.
- `check` cuenta pero no falla; los **umbrales** deciden el código de salida (99 si alguno se incumple).
- La carga se describe con `vus`/`duration`, `stages` o escenarios con *executors*: `ramping-vus` (modelo cerrado) o `constant-arrival-rate` (modelo abierto).
- La etiqueta `name` agrupa URLs y permite un umbral por petición. Un percentil global puede esconder una petición lenta.
- `--summary-export` guarda el resumen en JSON y `K6_WEB_DASHBOARD_EXPORT`, un informe HTML.
