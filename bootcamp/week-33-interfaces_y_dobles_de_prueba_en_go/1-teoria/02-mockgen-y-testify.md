# 02 - Mocks con mockgen y aserciones con testify

> Lenguaje: **Go**

La librería estándar no trae mocks ni aserciones: `if got != want { t.Errorf(...) }` es la forma de Go. Dos librerías cubren lo que la stdlib no da: `go.uber.org/mock` genera mocks a partir de una interfaz, y testify añade `assert`, `require` y su propio paquete de mocks. Esta teoría explica cómo se usan y cuándo compensan.

---

## 🎯 Objetivos

- Registrar mockgen como herramienta del módulo y generar un mock con `go generate`.
- Programar un mock con `EXPECT()`, `gomock.Any()`, `Times()` y `Return()`.
- Elegir entre `assert` y `require` de testify.
- Comparar `testify/mock` con mockgen.

---

## mockgen: el mock se genera

`go.uber.org/mock` es la continuación de `golang/mock`, el proyecto original de Google, archivado en 2023. Tiene dos partes:

| Parte | Qué es | Dónde va |
|---|---|---|
| `mockgen` | El programa que lee una interfaz y escribe el código del mock | Herramienta del módulo, con `go get -tool` |
| `gomock` | El paquete que usa ese código: `Controller`, `Any`, `Times` | Dependencia de los tests |

### 1. mockgen como herramienta del módulo

```bash
go get -tool go.uber.org/mock/mockgen@v0.6.0
```

**Qué:** añade la línea `tool go.uber.org/mock/mockgen` al `go.mod` (Go 1.24 o superior) y fija la versión en el bloque `require`.
**Para qué:** `go tool mockgen` ejecuta esa versión exacta, sin instalar nada en `$GOPATH/bin`.
**Impacto:** todo el equipo y la CI generan el mismo código. Con `go install mockgen@latest`, cada máquina tendría la versión del día en que la instaló.

### 2. La directiva `//go:generate`

```go
// Notifier envía un mensaje a un socio.
//
//go:generate go tool mockgen -destination=mock_notifier_test.go -package=reminders . Notifier
type Notifier interface {
	Notify(member, message string) error
}
```

`go generate ./...` busca las líneas `//go:generate` (sin espacio después de `//`) y ejecuta el comando que llevan. Las opciones de mockgen:

| Opción | Qué hace |
|---|---|
| `-destination=mock_notifier_test.go` | Escribe el mock en ese archivo. Como acaba en `_test.go`, solo existe al ejecutar los tests |
| `-package=reminders` | El paquete del archivo generado: el mismo que el del test, para usarlo sin importar nada |
| `. Notifier` | El paquete donde está la interfaz (`.` es el actual) y el nombre de la interfaz |

El archivo generado empieza con `// Code generated by MockGen. DO NOT EDIT.`, y se sube al repositorio: así `go test` funciona sin ejecutar antes `go generate`. Si cambias la interfaz y no lo regeneras, el test deja de compilar: `*MockNotifier does not implement Notifier (missing method ...)`.

### 3. Programar el mock

```go
func TestSendRemindersNotifiesEachOverdueLoan(t *testing.T) {
	ctrl := gomock.NewController(t)
	notifier := NewMockNotifier(ctrl)
	notifier.EXPECT().Notify("ana", "Dune: 3 días de retraso").Return(nil)
	notifier.EXPECT().Notify("eva", "Ulises: 12 días de retraso").Return(nil)

	s := &Service{Loans: newStore(), Notifier: notifier, Now: fixedClock}
	// ...
}
```

| Llamada | Qué hace | En Mockito ([semana 26](../../week-26-mockito_mocking_en_java/1-teoria/02-verify-y-captores.md)) |
|---|---|---|
| `gomock.NewController(t)` | Crea el controlador y registra con `t.Cleanup` la comprobación final | `MockitoExtension` |
| `EXPECT().Notify("ana", ...)` | Espera esa llamada con esos argumentos | `when(...)` + `verify(...)` en una sola línea |
| `.Return(nil)` | Lo que devuelve la llamada | `thenReturn` |
| `gomock.Any()` | Acepta cualquier valor en ese argumento | `any()` |
| `.Times(2)` | Exactamente dos llamadas. Sin `Times`, una | `times(2)` |
| `.DoAndReturn(func(...) error {...})` | Ejecuta una función con los argumentos reales | `thenAnswer` |

Un mock de gomock es **estricto**: una llamada sin `EXPECT` que la cubra hace fallar el test en el momento (`Unexpected call to ...`), y una expectativa que no se cumplió lo hace fallar al terminar (`missing call(s) to ...`). Un mock sin ningún `EXPECT` comprueba que el código **no** lo llame, como `verifyNoInteractions`.

## testify: `assert` y `require`

testify es la librería de aserciones más usada en Go. Sus dos paquetes principales tienen las mismas funciones; cambia qué pasa cuando fallan:

| Paquete | Al fallar llama a | Sigue el test | Úsalo para |
|---|---|---|---|
| `assert` | `t.Errorf` | Sí | Comprobaciones independientes: ver todos los fallos de una vez |
| `require` | `t.FailNow` | No | Lo que el resto del test necesita: un `err` que debe ser `nil`, un puntero que se va a usar |

```go
loan, err := s.MostOverdue()
require.NoError(t, err)                  // si falla, loan es nil: parar aquí
assert.Equal(t, "Ulises", loan.Title)    // el orden es (t, esperado, obtenido)
```

Es la misma diferencia que entre `t.Errorf` y `t.Fatalf` de la [semana 32](../../week-32-fundamentos_de_testing_en_go/1-teoria/01-go-test-y-el-paquete-testing.md). Con `assert.NoError`, el test sigue, `loan.Title` desreferencia un puntero nulo y el test termina en un `panic` ([lab 03](../2-practicas/lab-03-assert-require-y-testify-mock/README.md#experimento-2-assert-donde-hacía-falta-require)).

## testify/mock: el mock escrito a mano

testify trae también un paquete `mock`. No genera nada: el mock se escribe a mano, y cada método delega en `Called`:

```go
type mockNotifier struct {
	mock.Mock
}

func (m *mockNotifier) Notify(member, message string) error {
	args := m.Called(member, message)
	return args.Error(0)
}

// En el test
notifier.On("Notify", "ana", "Dune: 3 días de retraso").Return(nil).Once()
notifier.AssertExpectations(t)
```

| | mockgen + gomock | testify/mock |
|---|---|---|
| Código del mock | Generado con `go generate` | Escrito a mano, un método por método de la interfaz |
| Nombre del método en la expectativa | `EXPECT().Notify(...)`: lo comprueba el compilador | `On("Notify", ...)`: un texto, el error sale al ejecutar |
| Llamada inesperada | Falla el test | `panic` con el diff de la llamada más parecida |
| Comprobar que se cumplió todo | Automático, con `t.Cleanup` | Hay que llamar a `AssertExpectations(t)` |

En esta semana se usa mockgen para los mocks. testify/mock aparece en muchos proyectos, así que conviene saber leerlo.

---

## ✅ Resumen

- mockgen se registra con `go get -tool` y se ejecuta con una directiva `//go:generate go tool mockgen ...`.
- El mock generado se sube al repositorio y se regenera cuando cambia la interfaz.
- `EXPECT()` programa y verifica a la vez; el controlador comprueba lo pendiente al final del test.
- `require` para lo que el resto del test necesita; `assert` para lo demás.
