# Lab 02 - Mocks con mockgen

## Objetivo

Generar con mockgen un mock del `Notifier` del lab 01, programarlo con `EXPECT()`, `gomock.Any()`, `Times()` y `Return()`, y provocar los tres fallos que da un mock: una llamada inesperada, una llamada que falta y un mock viejo.

## Tiempo estimado

70 minutos.

## Preparación

```bash
cd starter
go mod download
go test -count=1 ./...
# ok  	bootcamp/lab02	0.002s [no tests to run]
```

`go mod download` descarga las versiones fijadas en `go.mod` y comprobadas en `go.sum`. El servicio es el del lab 01. `fakes_test.go` trae el reloj fijo y el almacén fake de ese lab, sin comentar.

Abre `go.mod`:

```text
module bootcamp/lab02

go 1.26.5

tool go.uber.org/mock/mockgen

require go.uber.org/mock v0.6.0
```

La línea `tool` registra mockgen como herramienta del módulo; se añadió con `go get -tool go.uber.org/mock/mockgen@v0.6.0` ([teoría 02](../../1-teoria/02-mockgen-y-testify.md#1-mockgen-como-herramienta-del-módulo)). Comprueba que funciona:

```bash
go tool mockgen -version
# v0.6.0
```

## Paso a paso

### Paso 1: generar el mock

En `reminders.go`, encima de `Notifier`, está la directiva:

```go
//go:generate go tool mockgen -destination=mock_notifier_test.go -package=reminders . Notifier
```

Ejecuta todas las directivas del módulo:

```bash
go generate ./...
ls
# fakes_test.go  go.mod  go.sum  mock_notifier_test.go  reminders.go  reminders_test.go
head -6 mock_notifier_test.go
# // Code generated by MockGen. DO NOT EDIT.
# // Source: bootcamp/lab02 (interfaces: Notifier)
# //
# // Generated by this command:
# //
# //	mockgen -destination=mock_notifier_test.go -package=reminders . Notifier
```

Busca en el archivo `func NewMockNotifier`, `func (m *MockNotifier) Notify` y `func (m *MockNotifier) EXPECT`. Son el constructor, el método que cumple la interfaz y el que usa el test para programar las llamadas. No edites el archivo: se reescribe cada vez que ejecutas `go generate`.

### Paso 2: un mock con los argumentos exactos (PASO 2)

1. En el import de `reminders_test.go`, descomenta `"testing"` y `"go.uber.org/mock/gomock"`.
2. Descomenta el bloque del PASO 2 y guarda.
3. Ejecuta:

   ```bash
   go test -count=1 -v ./...
   # --- PASS: TestSendRemindersNotifiesEachOverdueLoan (0.00s)
   # ok  	bootcamp/lab02	0.003s
   ```

| Línea | Qué hace |
|---|---|
| `gomock.NewController(t)` | Crea el controlador. Al terminar el test comprueba que se cumplieron todas las expectativas |
| `NewMockNotifier(ctrl)` | El mock generado, ligado al controlador |
| `EXPECT().Notify("ana", "Dune: 3 días de retraso")` | Espera una llamada con esos dos argumentos exactos |
| `.Return(nil)` | Lo que devuelve esa llamada: ningún error |

Compara con el lab 01: allí el test leía la lista del spy al final; aquí cada expectativa dice qué llamada debe ocurrir, y el mock la comprueba solo.

### Paso 3: cualquier argumento, un número de veces (PASO 3)

Descomenta el bloque del PASO 3:

```bash
go test -count=1 -run OneNotice -v ./...
# --- PASS: TestSendRemindersSendsOneNoticePerOverdueLoan (0.00s)
```

`Notify(gomock.Any(), gomock.Any())` acepta cualquier socio y cualquier mensaje, y `.Times(2)` exige exactamente dos llamadas. El test comprueba cuántos avisos salen, no cuáles: si mañana cambia el texto del aviso, no se rompe.

### Paso 4: un mock que devuelve un error (PASO 4)

1. En el import, descomenta `"errors"`.
2. Descomenta el bloque del PASO 4 y ejecuta:

   ```bash
   go test -count=1 -v ./...
   # --- PASS: TestSendRemindersNotifiesEachOverdueLoan (0.00s)
   # --- PASS: TestSendRemindersSendsOneNoticePerOverdueLoan (0.00s)
   # --- PASS: TestSendRemindersStopsAtFirstFailedNotice (0.00s)
   # ok  	bootcamp/lab02	0.002s
   ```

El mock espera **una** llamada para `ana` y devuelve `errDown`. Si el servicio siguiera con el aviso de `eva` después del error, esa segunda llamada no tendría expectativa y el test fallaría. Es lo que en el lab 01 comprobabas contando `len(notifier.sent)`.

## Experimentos

En los tres, la ruta que muestra el mensaje será la de tu copia del lab; aquí se abrevia como `<lab>`.

### Experimento 1: una llamada inesperada

En `TestSendRemindersNotifiesEachOverdueLoan`, borra la línea de la expectativa de `eva`:

```bash
go test -count=1 ./...
# --- FAIL: TestSendRemindersNotifiesEachOverdueLoan (0.00s)
#     reminders.go:52: Unexpected call to *reminders.MockNotifier.Notify([eva Ulises: 12 días de retraso]) at <lab>/reminders.go:52 because:
#         expected call at <lab>/reminders_test.go:13 doesn't match the argument at index 0.
#         Got: eva (string)
#         Want: is equal to ana (string)
```

El fallo sale en el momento de la llamada, en la línea 52 de `reminders.go`, y gomock compara con la expectativa más parecida: la de `ana`, que ya se usó. Deshaz el cambio.

### Experimento 2: una llamada que falta

En `TestSendRemindersSendsOneNoticePerOverdueLoan`, cambia `.Times(2)` por `.Times(3)`:

```bash
go test -count=1 ./...
# --- FAIL: TestSendRemindersSendsOneNoticePerOverdueLoan (0.00s)
#     controller.go:97: missing call(s) to *reminders.MockNotifier.Notify(is anything, is anything) <lab>/reminders_test.go:29
#     controller.go:97: aborting test due to missing call(s)
```

Este fallo no sale durante la llamada sino al terminar el test, cuando el controlador repasa lo pendiente. Nadie escribió esa comprobación: `NewController(t)` la registró con `t.Cleanup`. Deshaz el cambio.

### Experimento 3: el mock viejo

Añade a `Notifier` un segundo método, en `reminders.go`:

```go
type Notifier interface {
	Notify(member, message string) error
	NotifyAll(message string) error
}
```

```bash
go test -count=1 ./...
# # bootcamp/lab02 [bootcamp/lab02.test]
# ./reminders_test.go:16:45: cannot use notifier (variable of type *MockNotifier) as Notifier value in struct literal: *MockNotifier does not implement Notifier (missing method NotifyAll)
```

El mock se generó con la interfaz anterior. Regenéralo y vuelve a ejecutar:

```bash
go generate ./...
go test -count=1 ./...
# ok  	bootcamp/lab02	0.003s
```

Con un spy escrito a mano habrías tenido que añadir el método tú. Borra `NotifyAll` y regenera el mock con `go generate ./...`.

## Comprobación final

```bash
go generate ./... && go vet ./... && go test -count=1 ./...
# ok  	bootcamp/lab02	0.002s
```

## Preguntas de cierre

1. ¿Por qué el mock se genera en un archivo `_test.go` y no en uno normal?
2. En el PASO 3, ¿qué ganas y qué pierdes al usar `gomock.Any()` en lugar de los argumentos exactos?
3. El experimento 1 falla durante la llamada y el experimento 2 al terminar el test. ¿Por qué no pueden fallar los dos en el mismo momento?
