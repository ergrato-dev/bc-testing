# Lab 04 - Migraciones con Alembic

## Objetivo

Generar la migración de los modelos con Alembic y probar, contra el PostgreSQL de Testcontainers, que la migración sube, coincide con los modelos y baja.

## Tiempo estimado

60 minutos.

## Preparación

Docker debe estar en marcha, como en el lab 01.

```bash
cd starter
uv sync
uv run pytest -q
# no tests ran in 0.43s
```

Qué hay en `starter/`:

- **`pyproject.toml`:** añade `alembic` a las dependencias de los labs anteriores.
- **`models.py`:** los modelos `Book` y `Loan` de los labs anteriores.
- **`compose.yaml`:** un PostgreSQL de desarrollo para generar la migración (Paso 1). No lo usan los tests.
- **`tests/conftest.py`:** la fixture `postgres_url` del lab 01, ya completa.
- **`tests/test_migrations.py`:** comentado (PASOS 1 a 4).

La [teoría 04](../../1-teoria/04-migraciones-con-alembic.md) explica Alembic y qué se prueba de una migración.

## Paso a paso

### Paso 1: generar la migración con Alembic

1. **Arranca el PostgreSQL de desarrollo:**

   ```bash
   docker compose up -d --wait
   ```

   - `--wait` espera a que el `healthcheck` (`pg_isready`) confirme que acepta conexiones.
   - El puerto es `55432` y no `5432`, para no chocar con un PostgreSQL instalado en tu equipo.

2. **Crea la estructura de Alembic:**

   ```bash
   uv run alembic init migrations
   ```

3. **En `alembic.ini`**, cambia la línea `sqlalchemy.url`:

   ```ini
   sqlalchemy.url = postgresql+psycopg://library:library@localhost:55432/library
   ```

4. **En `migrations/env.py`**, sustituye `target_metadata = None` por:

   ```python
   from models import Base

   target_metadata = Base.metadata
   ```

5. **Genera la migración:**

   ```bash
   uv run alembic revision --autogenerate -m "create books and loans"
   # INFO  [alembic.autogenerate.compare.tables] Detected added table 'books'
   # INFO  [alembic.autogenerate.compare.tables] Detected added table 'loans'
   ```

6. **Abre el archivo nuevo de `migrations/versions/`.** `upgrade()` crea las dos tablas con sus restricciones y `downgrade()` las borra en orden inverso: primero `loans`, que depende de `books`.

7. **Para el PostgreSQL de desarrollo:**

   ```bash
   docker compose down
   ```

### Paso 2: la base de datos de migraciones (PASOS 1 y 2)

En `tests/test_migrations.py`, descomenta `alembic_config` y `table_names`.

- `alembic_config` crea una base de datos vacía, `migrations`, dentro del contenedor de Testcontainers y apunta Alembic hacia ella.
- `isolation_level="AUTOCOMMIT"` hace falta porque `CREATE DATABASE` no se puede ejecutar dentro de una transacción.
- `config.set_main_option` sustituye la URL de `alembic.ini`, que apunta al PostgreSQL de desarrollo, por la del contenedor.
- `table_names` lista las tablas de esa base de datos con `inspect`.

### Paso 3: `upgrade` y `check` (PASO 3)

Descomenta `test_upgrade_head_matches_the_models`. `command.upgrade` aplica la migración y `command.check` compara los modelos con la base de datos ya migrada: falla si hay diferencias.

### Paso 4: `downgrade` (PASO 4)

Descomenta `test_downgrade_base_removes_every_table` y ejecuta todo:

```bash
uv run pytest -q
# ..                                                                       [100%]
# 2 passed in 3.96s
```

### Paso 5: experimento, modelo sin migración

Añade una columna al modelo `Book`, debajo de `stock`, sin generar migración:

```python
    author: Mapped[str] = mapped_column(String(80))
```

```bash
uv run pytest -q
# E           alembic.util.exc.AutogenerateDiffsDetected: New upgrade operations detected: [('add_column', None, 'books', Column('author', String(length=80), table=<books>, nullable=False))]
# 1 failed, 1 passed in 3.92s
```

Ese test es el que impide que un modelo nuevo llegue a producción sin su migración. Borra la línea `author`.

## Preguntas de cierre

1. ¿Por qué `alembic_config` crea una base de datos nueva en lugar de usar la del contenedor tal cual?
2. ¿Qué pasaría en producción si `downgrade()` borrara `books` antes que `loans`?
